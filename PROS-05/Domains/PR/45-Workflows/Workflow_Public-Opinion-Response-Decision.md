# Workflow: Public Opinion Response Decision

## 用户任务

用户遇到一个负面、争议、爆料、投诉、误读或热点牵连事件，需要判断：

- 要不要回应。
- 谁来回应。
- 什么时候回应。
- 用什么格式回应。
- 回应到什么程度。
- 哪些内容不能说。
- 是否需要先做内部动作。

这个 Workflow 不直接默认生成声明。

核心判断：危机回应不是写一句话，而是在事实、责任、情绪、平台、格式和组织动作之间做匹配。

---

# 判断来源优先级

本Workflow按知识库当前治理顺序运行：

1. 当前有效的Principle、Framework、Strategy与经过Evidence支持的案例，提供专业判断和适用边界。
2. 本Workflow定义输入、追问、步骤、输出和门禁；用户当前业务事实决定实际结论。
3. Skill负责调用适配、工具使用和交付门禁。Skill反馈只有复核并写回知识层或本Workflow后，才成为上游判断来源。
4. 经典理论只用于校准机制与边界，不作为前台表达主轴。

重点知识入口包括案例库中的事实链与不可照搬点、危机事实与分阶段披露策略、利益相关方回应顺序策略、争议事实证据沟通策略，以及公共舆论格式、平台传播与SCCT等框架。理论框架用于：

- 帮助确认责任归因是否和回应强度匹配。
- 帮助识别公众真正审判的问题。
- 帮助避免回应格式弱于爆料格式。

理论不作为前台表达主轴，不把用户带进学术解释。

## Workflow与Skill职责边界

- 本Workflow定义一份最终结果必须完成哪些判断，不要求机械串行调用全部Skill。
- `hot-public-opinion-analysis`、`media-narrative-analysis`等专项Skill先完成各自新增职责。
- 只有仍存在是否回应、动作优先级、暂停条件或组织承诺取舍时，才把八字段交接包交给`judgment-hub`作最终决策。
- `copy-lens-review`只审查已经形成的回应文本，不重复判断事件是否成势。
- 同一事实、框架和业务影响不在上下游重复读取或重写。

本Workflow只允许两种运行方式：

1. **直接模式**：本Workflow是唯一执行入口，由同一执行者完成Step1—8并交付最终结果，不再转入`judgment-hub`重做取舍。
2. **Skill链模式**：专项Skill完成舆情状态、实质、条件走势、责任边界和风险暴露后停止，用八字段交接包转入`judgment-hub`；后者只完成Step4—8中的回应取舍、姿态、形式、暂停条件与复盘。上游不得先给一遍最终回应决策。

两种模式不能在同一任务叠加。`copy-lens-review`只审查已经形成的回应文本，不重启Step1—4。

# 适用场景

## 适用

- 消费者投诉形成公开讨论。
- 截图、录音、检测报告、短视频、长文或 PDF 引发争议。
- 品牌被质疑产品、服务、价格、价值观或高管言论。
- 谣言、误读或不完整信息开始扩散。
- 媒体、KOL、用户或内部员工发布负面内容。
- 品牌被卷入行业热点、公共事件或竞品争议。

## 不适用

- 事实完全不清，但用户要求直接发布最终声明。
- 涉及法律、监管、食品安全、数据安全或人身安全，且没有内部确认机制。
- 用户要求伪造第三方、隐藏事实、诱导公众或有偿删帖。
- 事件本质不是传播问题，而是产品、服务、组织或合规问题。

遇到不适用场景，应先要求补充事实、证据和内部处置动作。

# 输入字段

## 必填

### 0. 判断主体与时间锚点

必须说明：

- 当前替涉事组织、同行品牌、渠道／平台还是其他主体决策。
- 判断对应的日期、时段或事件阶段。
- 用户要判断历史处置，还是当前是否仍需动作。

缺少主体或时间锚点且会改变结论时，只给条件判断，不把合理假设伪装成用户事实。

### 1. 事件概述

用户需要说明：

- 发生了什么。
- 谁在说。
- 说了什么。
- 目前影响到谁。

### 2. 已确认事实

至少区分：

- 已确认事实。
- 单方说法。
- 待核实信息。
- 明确不实信息。
- 暂不可公开信息。

### 3. 传播状态

需要说明：

- 首发平台。
- 当前主要传播平台。
- 是否跨平台扩散。
- 是否有媒体、KOL、营销号或社群参与。
- 评论区高频情绪。

### 4. 品牌责任边界

需要说明：

- 品牌是否直接相关。
- 是否有产品、服务、员工、渠道、合作方或高管责任。
- 品牌已经做了什么。
- 品牌能承诺什么，不能承诺什么。

### 5. 时间要求

需要说明：

- 什么时候被发现。
- 目前是否仍在发酵。
- 用户希望多久内给出判断。

# 核验、澄清与公开边界

先核对已有事实、单方说法、责任、补救动作与发布授权。产品／食品／健康／数据安全、监管或刑事主题本身不要求再次确认；实际事实和承诺决定能说什么。

缺口会改变事实责任、组织承诺或关键外部行动时，只暂停对应主张／动作并补问，其余审查、条件分支和工作稿继续完成。已有明确授权不重复索取；可发布终稿须解决影响发布的事实与权限缺口。

对无依据的道歉承诺、反击或推责，说明证据限制并提供可信替代。不得把删帖压热度、买通发布方或伪造第三方包装成正常执行路径，也不通过追问取得这种做法的许可。

# 判断流程

公开材料核验复用已有范围、索引与结论，只补会改变判断的缺口。多来源检索记录实际查询、目标材料和返回字段；每条材料分开记录实际阅读状态、保存形式、日期及内容覆盖。同源转载可作为传播节点，不能重复计算为独立事实或公众态度证据。关键冲突先明确目标证据和完成条件，补证后重新核验并更新受影响的事实、时间线和交接包；未解决则限制对应判断，其他分析与必要保护动作继续。

以下步骤是最终结果的任务合同。直接模式由一个执行者完成全部步骤；Skill链模式由上游完成Step1—3和风险暴露，`judgment-hub`完成Step4—8。不得把完整流程执行两遍。

## Step 1: 判断真正问题

先判断事件主要属于哪一类：

- 事实争议。
- 产品或服务问题。
- 价值观争议。
- 谣言或误读。
- 员工或高管言论。
- 合作方或渠道问题。
- 平台格式放大。
- 行业热点牵连。

输出：

- 当前问题类型。
- 这是不是 PR 能独立解决的问题。
- 是否需要业务、法务、客服、产品、供应链或管理层介入。

## Step 2: 拆解舆论五层

按五层模型判断：

### 事实层

- 哪些事实已确认。
- 哪些信息仍在核实。
- 哪些说法明显不实。
- 哪些事实影响责任归因。

### 格式层

- 事件以什么格式传播。
- 这个格式天然制造了什么可信度暗示。
- 品牌回应格式是否需要匹配爆料格式。

### 平台层

- 哪个平台在放大事件。
- 平台奖励的是愤怒、反转、玩梗、维权、事实核查还是价值审判。
- 哪些节点可能二次加工。

### 身份层

- 谁会觉得这件事和自己有关。
- 是否触发消费者、员工、女性、打工人、养宠人、粉丝或行业从业者身份。

### 道德层

- 公众最终在审判什么。
- 是事实错误、态度傲慢、权力滥用、商业欺骗、价值观冒犯，还是组织不负责任。

输出：

- 公众真正关心的问题。
- 品牌如果只回应事实会漏掉什么。
- 当前最危险的误读方向。

涉及检测报告、实测视频、合规或反转争议时，按[争议事实与证据沟通策略](../40-Strategies/Strategy_Disputed-Facts-Evidence-Communication.md)核对是否为同一主张及可比条件。输出保留各组样本、条件和结果的对应关系；分别说明事实争议、补救兑现与公众反应的已知状态和缺口。不用一项检测、组织承诺或传播下降代替整体结案，不扩张为本Workflow自行完成工程鉴定。

## Step 3: 判断责任归因

使用 SCCT 回应匹配逻辑，判断公众认为品牌责任处于哪一级：

| 责任归因 | 判断信号 | 回应方向 |
| --- | --- | --- |
| 低 | 品牌被牵连，事实责任弱 | 事实告知、风险提示、持续更新 |
| 中 | 品牌有管理、服务或沟通责任 | 解释原因、表达关怀、说明处置 |
| 高 | 品牌存在明显过失或伤害 | 道歉、补偿、纠偏、负责人机制 |
| 已被价值审判 | 公众已默认品牌价值有问题 | 行动优先，价值回应跟上 |

输出：

- 公众责任归因等级。
- 品牌真实责任边界。
- 两者是否错位。

## Step 4: 判断是否回应

回应决策不是二选一，而是五种选择：

| 决策 | 适用条件 | 风险 |
| --- | --- | --- |
| 不回应 | 低传播、低共鸣、无事实伤害 | 可能被认为默认或傲慢 |
| 暂缓回应 | 事实未清，但需要内部核实 | 窗口期流失 |
| 定向沟通 | 影响范围有限，有明确对象 | 被截图后可能外溢 |
| 轻回应 | 需要表达关注或澄清局部事实 | 可能被认为避重就轻 |
| 正式回应 | 传播扩散、责任明确或公众期待高 | 表达和行动必须承受追问 |

判断问题：

- 如果不回应，事件是否自然衰减。
- 如果回应，是否会扩大传播。
- 如果暂缓，是否需要先发布「正在核实」。
- 如果正式回应，是否有行动支撑。

输出：

- 回应必要性。
- 推荐回应等级。
- 不推荐选项及原因。

## Step 5: 选择回应姿态

根据责任归因和舆论情绪选择组合姿态：

- 告知。
- 关怀。
- 解释。
- 澄清。
- 道歉。
- 补偿。
- 整改。
- 反击。
- 持续更新。

原则：

- 低责任不应过度道歉。
- 中责任不能只讲流程。
- 高责任不能先争辩。
- 已被价值审判时，行动比措辞更重要。
- 反击只适合证据极硬、责任边界清楚、公众情绪可承受的场景。

输出：

- 推荐回应姿态。
- 禁用姿态。
- 姿态选择理由。

## Step 6: 设计回应格式

不要用单一声明应对所有传播格式。

匹配建议：

| 舆论格式 | 回应格式 |
| --- | --- |
| 短视频切片 | 短解释 + 长版事实说明 |
| 聊天截图 | 恢复语境 + 明确边界 |
| PDF / 长文 | 逐条回应 + 事实表格 |
| 检测报告 | 专业解释 + FAQ |
| 评论区高赞 | 高频问题回应 |
| 谣言复燃 | 搜索友好型澄清 + 证据页 |

输出：

- 首发渠道。
- 回应形式。
- 是否需要 FAQ、长文、短声明、客服口径、媒体沟通或高管表达。

## Step 7: 形成对外口径框架

口径不先追求漂亮，而先追求可承受追问。

基本结构：

1. 我们已经注意到什么。
2. 已确认事实是什么。
3. 仍在核实什么。
4. 我们理解公众为什么关心。
5. 我们已经采取或将采取什么动作。
6. 下一次更新在什么时候。
7. 哪些信息可以通过什么渠道继续沟通。

如果是谣言或误读，补充：

- 不实点逐条澄清。
- 可验证证据。
- 权威信源。
- 后续复燃处理机制。

如果是高责任归因，补充：

- 道歉对象。
- 具体补救。
- 负责人机制。
- 复盘和整改时间表。

输出：

- 口径框架。
- 可公开句式。
- 不可说内容。
- 待确认事实。

## Step 8: 设置复盘和更新

事件结束后判断：

- 是否应沉淀为案例。
- 是否验证或挑战已有框架。
- 是否需要更新 Workflow。
- 是否需要进入 Skill 测试用例。

输出：

- 复盘问题。
- 知识沉淀建议。

# 成熟度要求

当前成熟度：Level 1草案。已有Skill适配器完成过单次真实任务，不等于本Workflow已经跨场景稳定。

升级到 Level 2 需要：

- 至少 3 次真实舆情任务使用。
- 每次记录输入、输出、人工修改点和最终结果。
- 至少补充 3 个关联案例。

升级到 Level 3 需要：

- 明确常见失败模式。
- 形成不同事件类型的回应样例。
- 输出稳定达到 B 级以上。

升级到 Level 4 需要：

- 非维护者可独立使用。
- 表单、输出和评分稳定。
- 可以作为产品任务页上线。

升级到 Level 5 需要本Workflow能够作为稳定Skill的来源合同，并使关联Skill具备成功、暂停、失败与跨场景回归证据。
